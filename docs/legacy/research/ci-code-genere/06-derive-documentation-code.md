# Fitness functions, conformance checking et détection de dérive document ↔ document : état 2025-2026 et options CI

## TL;DR
- **La doctrine des fitness functions et de l'architectural conformance checking (ACC) est mûre et bien outillée pour le code ↔ architecture, mais elle ne traite quasiment PAS la dérive document ↔ document** : le seul corpus académique proche (ArDoCo / Keim et al., ICSA 2023) détecte les incohérences entre *texte de documentation* et *modèle d'architecture formel*, pas entre deux documents de gouvernance comme un ADR et son invariant. [INCERTAIN sur document ↔ document — voir section 2].
- **Puisque tu n'as pas encore de code, la plupart des outils de conformance (ArchUnit, dependency-cruiser, ArchUnitTS) sont prématurés** : ils vérifient des dépendances de code inexistantes. Ce qui est déployable *maintenant* est une combinaison de contrôles textuels/structurels sur ton corpus Markdown : lint de structure, intégrité des liens croisés, invariants de statut d'ADR, et « fitness functions pour décisions » au sens de Joel Parker Henderson.
- **Pour la documentation exécutable JS/TS en CI, markdown-doctest et txm sont effectivement morts, mais il existe des remplaçants actifs en 2026** : `typescript-docs-verifier` (compile les blocs TS), `@eslint/markdown` (lint), `codedown` (extraction), et `deno test --doc` (compile + exécute). C'est la partie de ta question la mieux résolue.

## Key Findings

1. **Fitness function = « tout mécanisme fournissant une évaluation objective de l'intégrité d'une ou plusieurs caractéristiques architecturales »** (définition de Ford/Parsons/Kua, *Building Evolutionary Architectures*, reprise par Thoughtworks). Concept-socle stable de 2017 à la 2e édition (2022) et jusqu'en 2025-2026.
2. **L'ACC compare une architecture *intentionnelle* (fournie par l'architecte) à une architecture *implémentée* (extraite du code source)** — c'est du code ↔ architecture par construction (Li/Liang/Avgeriou, arXiv 2306.08616). Extrapoler ce cadre vers document ↔ document est une extrapolation, signalée comme telle.
3. **Le seul travail primaire proche de ton besoin est ArDoCo (Keim et al., ICSA 2023)** : détection d'incohérences entre documentation en langage naturel et modèle formel via traceability link recovery (TLR), F1 de 0,81. Mais cela suppose un *modèle d'architecture formel* comme second artefact, pas un second document en prose.
4. **Il existe une doctrine émergente, non académique, de « fitness functions for decisions as code » (Joel Parker Henderson)** qui étend explicitement l'idée aux ADR et propose même des checks assistés par LLM. Source secondaire/praticienne, pas de la recherche évaluée.
5. **Les remplaçants de markdown-doctest/txm existent et sont maintenus en 2026** ; distinction clé : *compiler* (type-check) vs *exécuter*.
6. **La littérature « configuration drift » et « API/spec drift » est abondante mais concerne l'infra (Terraform/IaC) et OpenAPI** — pertinente par analogie pour ton incident CI ↔ forge, mais pas directement transposable à la gouvernance ADR/invariants.

## Details

### 1. Doctrine des fitness functions et de l'architectural conformance checking (état 2025-2026)

**Définition et taxonomie (source primaire : livre + Thoughtworks).** La définition canonique est celle de *Building Evolutionary Architectures* (Neal Ford, Rebecca Parsons, Patrick Kua) : une fitness function « provides an objective integrity assessment of some architectural characteristic ». La 2e édition (O'Reilly, 2022, préface signée Mark Richards, octobre 2022) structure les catégories selon plusieurs axes, listés dans la table des matières : **Scope** (Atomic vs Holistic), **Cadence** (Triggered vs Continual vs Temporal), **Result** (Static vs Dynamic), **Invocation** (Automated vs Manual), **Proactivity** (Intentional vs Emergent), **Coverage** (Domain-Specific). Le livre traite aussi de « Documenting Fitness Functions » et « Fitness Functions as a Checklist, Not a Stick ». Un cas d'usage s'intitule « Validating API Consistency in an Automated Build » — le plus proche de ton incident CI ↔ forge.

**Outillage 2025-2026 (sources primaires : dépôts + docs).**
- **ArchUnit** (Java) reste la référence pour les fitness functions structurelles ; le dépôt `thmuch/architecture-fitness-functions` illustre ArchUnit + jMolecules.
- **ArchUnitTS** (Lukas Niessen) est le pendant TypeScript, revendiqué par l'auteur comme « the #1 architecture testing framework in the TypeScript world » par nombre d'étoiles GitHub (« just hit 200 stars on GitHub », octobre 2025). Fonctionne avec Jest, Vitest, Jasmine, Mocha. Particularité utile : « Empty Test Protection » — un test qui matche 0 fichier (typo dans un chemin) échoue au lieu de passer silencieusement. Version v2.3.3 documentée fin 2025.
- **dependency-cruiser** (npm handle : `sverweij`) : « validate and visualize dependencies, your rules » pour JS/TS. Version **18.2.0** (npm : « Latest version: 18.2.0, last published: 3 days ago » en août 2026), ~2,6–3,1 millions de téléchargements/semaine selon la source (Snyk : « 2,628,013 downloads a week » ; revue MrKeyoor : « 3,122,239 downloads for the measured week »), dépôt poussé le 8 août 2026 — très actif. Il permet des règles `forbidden`, `allowed`, `required` (ex. « tout controller doit dépendre du base controller » ; « controllers must not use repositories directly »), exécutables en CI comme un linter structurel.
- Thoughtworks Technology Radar classe encore la « architectural fitness function » comme technique établie.

**Limite décisive pour ton projet :** tous ces outils analysent des *dépendances de code*. **Tu n'as pas de code.** ArchUnitTS et dependency-cruiser sont donc à préparer (écrire les règles à partir de tes invariants) mais pas à déployer utilement tant que `src/` est vide. C'est un point de séquençage, pas de rejet.

**ACC — cadrage académique (sources primaires arXiv consultées).**
- arXiv 2306.08616 (Li, Liang, Avgeriou, *Towards Automated Identification of Violation Symptoms of Architecture Erosion*, version ACM TOSEM 2024) définit l'érosion comme « the increasing and accumulating divergences between implemented and intended architecture » et positionne l'ACC ainsi : « comparing the structure of the intended architecture (provided by the architects) with the extracted architecture information from source code ». Contribution : identifier les *symptômes de violation* dans des artefacts textuels (commentaires de code review) via ML/DL. Résultat verbatim (version TOSEM) : « the SVM classifier based on word2vec performed the best with a Precision of 0.789, a Recall of 0.828, an F1-score of 0.808, and an Accuracy of 0.803 » (une version ultérieure v6 rapporte aussi GPT-4o comme meilleur classifieur LLM à F1 0,851). C'est textuel, mais toujours ancré au code.
- arXiv 2401.16382 (REMEDY) est un ACC spécialisé pour systèmes auto-adaptatifs MAPE-K : DSL pour l'architecture planifiée + extraction de l'architecture implémentée + moteur de conformité. Encore code ↔ architecture. Verbatim : « As SASs evolve, implementations can drift from the intended MAPE-K architecture… Architectural Conformance Checking (ACC) addresses this risk by comparing the current implementation to a specification of the architecture. »

**Conclusion angle 1 :** la doctrine est solide, outillée, et — pour un projet sans code — surtout utile comme *vocabulaire* (atomic/holistic, triggered/continual) et comme *cible future*. Aucune de ces sources ne traite la cohérence entre deux documents de prose.

### 2. Cohérence document ↔ document (le cœur de ta question)

**[INCERTAIN] Aucune source consultée ne traite spécifiquement la dérive entre deux documents de gouvernance** (par exemple entre un ADR et l'invariant qu'il devrait faire respecter, ou entre une source de vérité de configuration et les points de code qui en dépendent *avant* que le code existe). Ce qui existe se répartit en trois familles voisines, dont aucune ne recouvre exactement ton cas :

**(a) Détection d'incohérences documentation ↔ modèle (le plus proche — ArDoCo, source primaire).** Keim, Corallo, Fuchß, Koziolek, *Detecting Inconsistencies in Software Architecture Documentation Using Traceability Link Recovery* (ICSA 2023, DOI 10.1109/ICSA56044.2023.00021). Citation verbatim : « there can be inconsistent information in different SADs for the same system. Inconsistent documentation then can cause flaws in development and maintenance. » L'approche détecte deux types d'incohérence : les *unmentioned model elements* (éléments du modèle sans documentation en langage naturel — renommés « Model Entity Absent from Text / MEAT » dans ArDoCo v2) et les *missing model elements* (décrits mais non modélisés — renommés « Text Entity Absent from Model / TEAM »). Résultats verbatim (page auteurs ardoco.de/c/icsa23) : « For TLR, we achieve an excellent F1-score of 0.81, significantly outperforming the other approaches by at least 0.24. Our approach also achieves excellent results (accuracy: 0.93) for detecting unmentioned model elements and good results for detecting missing model elements (accuracy: 0.75). » **Limite pour toi :** le second artefact est un *modèle formel* (diagramme/PCM), pas un second document en prose ; et l'approche est un outil de recherche (ArDoCo), pas un check CI clé-en-main.

**(b) Traçabilité des exigences (source secondaire + primaire).** La discipline « requirements traceability » (Gotel & Finkelstein ; Cleland-Huang et al.) traite la cohérence inter-artefacts, mais orientée exigence → test → code, via une matrice de traçabilité (RTM). Un article arXiv récent (ReqToCode) propose de comparer les timestamps : si une exigence est modifiée après le dernier commit du code qui la référence, on émet un « signal de visibilité » de dérive potentielle sans casser le build (verbatim : « This does not produce a build error… but it produces a visibility signal that enables teams to assess whether the implementation still satisfies the updated requirement »). **C'est l'idée la plus directement transposable à ton corpus** : traiter chaque ADR/invariant comme une « exigence » et surveiller les décalages temporels de modification. Mais c'est une extrapolation de ma part, à signaler.

**(c) Software aging / specification drift (source secondaire).** Parnas a identifié le « software aging » : la précision de la documentation se dégrade à mesure que le système évolue. Un case study arXiv (audit de specs de prompts) rapporte que 23,5 % des défauts étaient des références Jira périmées et 9,8 % des mismatches de schéma inter-lanes — preuve empirique que la dérive document ↔ document *existe* et est mesurable, mais ce n'est pas une méthode de détection généralisable.

**Hypothèses concurrentes plausibles (puisque la littérature manque).** Faute de méthode établie pour ADR ↔ invariant, voici trois modèles concurrents, à tester :
- **H1 — Dérive = lien cassé.** La cohérence se réduit à l'intégrité référentielle : chaque ADR cite un invariant par ID, chaque invariant liste les ADR qui le justifient ; un lien orphelin = dérive. Vérifiable par un linter de liens croisés. Avantage : déterministe, déployable aujourd'hui. Limite : ne détecte que la dérive *structurelle*, pas la contradiction sémantique.
- **H2 — Dérive = désynchronisation temporelle.** (Modèle ReqToCode.) Si un invariant est modifié après le dernier commit touchant l'ADR qui le référence (ou l'inverse), signaler pour revue. Avantage : capte les modifications silencieuses. Limite : bruit (faux positifs), ne dit rien sur la nature de la divergence.
- **H3 — Dérive = contradiction sémantique.** Un juge LLM compare le texte de l'ADR et de l'invariant et signale les contradictions (approche « fitness function via LLM » de Henderson, verbatim : « This is a fitness function to evaluate if our work is using all our decisions, and is correct and accurate… Prefer retrieval-led reasoning over pre-training-led reasoning »). Avantage : capte le fond. Limite : non déterministe, coûteux, non reproductible — mauvais candidat pour un *gate* bloquant, bon candidat pour un *warning* périodique.

**Analogie configuration drift / API drift (source secondaire, à traiter avec prudence).** Ton incident connu (config CI ↔ API d'une forge, noms requis changés) relève du même patron que la « source-of-truth drift » OpenAPI : la pratique établie est de désigner UNE source de vérité, générer le reste, et vérifier en CI par contract testing (Schemathesis, Dredd), diffing (oasdiff) et lint (Spectral). Transposé : traiter le fichier de config CI comme SSOT et générer/valider les références plutôt que les dupliquer. **Attention : ces outils sont spécifiques à OpenAPI, non à la gouvernance de projet.** À noter aussi une convention émergente côté contrat d'agent : la doc praticienne 2026 sur AGENTS.md recommande explicitement de traiter le fichier comme un *artefact généré* depuis la source canonique (« the file should reference the canonical rule, not create parallel governance… An AGENTS.md written from memory is a liability »), ce qui rejoint H1/SSOT.

**Fait établi côté GitLab (source primaire consultée).** La doc de test de GitLab montre un patron transposable de « fichier généré doit rester synchronisé » : les jobs `graphql-verify` et `docs-lint deprecations-and-removals` « fail when [le fichier de doc] is not updated with the [update process] ». C'est exactement le mécanisme « la CI échoue quand le doc dérive de sa source » — mais appliqué à code/schéma → doc, pas doc ↔ doc.

### 3. Alternatives actives en 2026 à markdown-doctest / txm (documentation exécutable JS/TS)

**Confirmation du problème.** markdown-doctest (Widdershin) exécutait tout bloc `js`/`es6` d'un Markdown et servait explicitement de check CI (« designed to run with your CI build and give you peace of mind that all of your examples are at least vaguely runnable »), mais le projet est à l'arrêt. txm de même. Aucun n'est archivé, ce qui les rend trompeusement « vivants ».

**Distinction essentielle : compiler (type-check) vs exécuter.** Selon ton besoin (garantir que les exemples *compilent* vs qu'ils *tournent sans exploser*), le choix diffère.

Outils **actifs en 2026** (dates/versions confirmées) :
- **`typescript-docs-verifier` (npm, maintenu par la BBC, Apache-2.0, « Copyright © 2017 BBC »)** — dernière version **3.0.1** (npm : « Latest version: 3.0.1, last published: 2 months ago », ~juin 2026). **Compile mais n'exécute pas** : verbatim « Each code snippet is compiled (but not run) and any compilation errors are reported. » Idéal pour vérifier que les extraits TS d'un ADR ou d'un contrat d'agent compilent contre ton `tsconfig`. **C'est mon premier choix pour ton cas TS greenfield.**
- **`@eslint/markdown` (npm)** — dernière version **7.5.1** (~avril 2026), 219 dépendants, requiert ESLint ≥ 9.15. **Lint uniquement** (extrait les blocs et les passe aux règles ESLint : JS, JSX, TS). Ne compile ni n'exécute. Successeur de `eslint-plugin-markdown` (5.1.0, figé depuis ~2 ans).
- **`codedown` (npm, earldouglas)** — **3.2.1** (~janvier 2026). **Extrait seulement** les blocs vers stdout (`cat README.md | codedown ts | ...`) ; agnostique au langage, tu pipes vers ton compilateur/exécuteur. Utile comme brique de composition.
- **`deno test --doc`** — intégré au runtime Deno, maintenu en continu. **Compile ET exécute** les exemples TS/JS des blocs Markdown et des JSDoc. La meilleure option « tout-en-un » *si* une toolchain Deno est acceptable (elle l'est facilement pour un projet TS greenfield).
- **`runmd` (npm, broofa/Robert Kieffer)** — **[CONFLIT DE SOURCES]** : le miroir UNPKG indique une version **2.1.1** (~avril 2026), mais la page npm officielle affiche encore « Latest version: 1.4.1, last published: a year ago » et le registre ne confirme pas 2.1.1. **Traite ce statut comme incertain et vérifie le dist-tag `latest` avant adoption.** Comportement (verbatim) : « RunMD scripts are run using Node.js' vm module… console.log() works, but no other console methods are supported… setTimeout() works, but all timers fire immediately… clearTimeout, setInterval, and clearInterval are not supported. » **Exécute** les blocs JS ; convient seulement à des exemples déterministes courts.

Outils **abandonnés / obsolètes** (à éviter) :
- **`@btilford/md-check`** — 1.0.1, publié il y a ~6 ans ; le compagnon `-compile-typescript` marqué inactif. Abandonné.
- **`@andrewbrey/mdrb` (JSR/Deno)** — 3.0.4, ~2023, ~2 ans sans release ; fonctionnel (exécute TS/JS avec `dax` injecté) mais stagnant.
- Utilitaires « extract-only » anciens (markdown-code-extractor, gfm-code-blocks, etc.) : 9-12 ans, à ignorer.

## Recommendations

Stratégie en trois vagues, adaptée à un dev solo, projet TS greenfield, corpus = ~30 ADR + invariants + contrat d'agent.

**Vague 0 — Déployable aujourd'hui, sans code (gates bloquants) :**
1. **Lint de structure Markdown + front-matter obligatoire** (modèle GitLab : chaque doc doit contenir un front-matter d'appartenance ; markdownlint pour la structure). Impose un template d'ADR strict (Status ∈ {Proposed, Accepted, Superseded}, IDs, liens).
2. **Check d'intégrité des liens croisés (H1).** Un script CI qui vérifie : chaque ADR référence ≥ 1 invariant existant par ID ; chaque invariant liste les ADR qui le justifient ; aucun lien orphelin ; aucun ADR superseded sans lien réciproque. C'est l'ACC transposé au niveau documentaire — **dis explicitement dans ta doc que c'est une transposition, pas de l'ACC au sens de la littérature.**
3. **Invariant d'append-only sur les ADR** (règle Microsoft/Nygard : un ADR accepté ne se modifie pas, il se supersede — « If a decision changes, write a new record that supersedes the original and link the two together »). Vérifiable via git : refuser en CI toute modification du corps d'un ADR au statut « Accepted » sans changement de statut.
4. **Documentation exécutable des extraits TS présents dans les ADR/contrat d'agent** : `typescript-docs-verifier` (compile) comme gate. Si tu veux aussi *exécuter*, ajoute `deno test --doc` (préférable à runmd, dont le statut de version est incertain).

**Vague 1 — Quand la config CI ↔ forge réapparaît (ton incident connu) :**
5. **Désigner une SSOT unique** pour les noms de checks/jobs et générer les références plutôt que les dupliquer ; valider en CI qu'aucune référence ne pointe vers un nom inexistant (patron GitLab `graphql-verify` / analogie oasdiff-Spectral, transposé). Même patron pour le contrat d'agent : le générer depuis la source canonique plutôt que le maintenir « de mémoire ». Seuil de déclenchement : toute PR touchant la config CI ou le contrat d'agent.

**Vague 2 — Quand `src/` commence à se remplir :**
6. **Écrire les fitness functions structurelles maintenant, les activer plus tard.** Traduire chaque invariant d'architecture en règle `dependency-cruiser` (`forbidden`/`required`) et/ou test **ArchUnitTS** (avec Empty Test Protection activée pour éviter les tests vides trompeurs). Elles échoueront « à vide » tant qu'il n'y a pas de code, donc marque-les `pending`.
7. **Fitness functions pour décisions (Henderson).** Pour chaque ADR à section « Compliance », spécifier le test qui l'assure. Décisions structurelles → règle dependency-cruiser/ArchUnitTS ; décisions à hypothèses externes (version de framework, tier de pricing) → check périodique.

**Contrôles NON bloquants (warnings / cron) :**
8. **H2 (désynchronisation temporelle)** et **H3 (contradiction sémantique via LLM)** : en `warning` hebdomadaire, jamais en gate bloquant (trop de bruit / non déterministe).

**Benchmarks qui changeraient ces recommandations :**
- Si tu adoptes une toolchain Deno → bascule la doc exécutable sur `deno test --doc` (remplace typescript-docs-verifier + runmd).
- Dès que `src/` dépasse quelques modules → active les gates dependency-cruiser/ArchUnitTS.
- Si les faux positifs de H2 dépassent ~1 par PR → repli sur H1 seul.
- Si ArDoCo publie un outil autonome ADR ↔ prose → réévaluer H3.

## Caveats
- **Distinction fait/interprétation :** la définition des fitness functions et la taxonomie ACC sont des *faits établis* (sources primaires : livre, arXiv 2306.08616 et 2401.16382, Thoughtworks, ArDoCo). L'application au niveau document ↔ document est mon *interprétation/extrapolation*, explicitement signalée.
- **[INCERTAIN] persistant :** aucune source évaluée par les pairs ne traite la dérive ADR ↔ invariant ni config-SSOT ↔ code-avant-existence. ArDoCo (doc ↔ modèle formel) et ReqToCode (exigence ↔ code) sont les plus proches mais ne recouvrent pas ton cas.
- **Sources praticiennes vs académiques :** « fitness functions for decisions as code » (Henderson) et les guides AGENTS.md sont des sources secondaires/praticiennes, non évaluées ; à traiter comme des conventions émergentes, pas comme des preuves.
- **Produits commerciaux (Mintlify, GitBook, Redocly, Fern) :** délibérément non approfondis — leur usage typique est la dérive de doc d'API/OpenAPI, hors de ta cible gouvernance (ADR/invariants). Mentionnés pour complétude seulement.
- **Dates de versions :** issues des pages npm/JSR/UNPKG au moment de la recherche (août 2026) ; npm affiche des dates relatives, converties en approximations. **Conflit de sources non résolu sur `runmd`** (npm : 1.4.1 il y a ~1 an ; UNPKG : 2.1.1 ~avril 2026) — vérifie le dist-tag avant adoption ; un conflit de cache similaire a été observé sur typescript-docs-verifier (2.5.3 périmé vs 3.0.1 live), où la version live fait foi.
